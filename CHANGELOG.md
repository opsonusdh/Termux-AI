## [Unreleased]

### Fixed
- **The sub-agent registry had drifted away from its own evidence** (`core/models.py`, `tests/fixtures/subagent_tool_calling.json`): four routes were only half-registered, so the two guards the project runs on — *free AI only* and *tool-calling only* — rejected the very models the tiers were routing. The suite was red with `paid routes registered: [('ollama', 'nemotron-3-nano:30b')]`, `models without verified tool calling: [('medium', 'ollama', 'gemma4:31b'), ('low', 'ollama', 'nemotron-3-nano:30b')]`, `gate entries without live evidence: ['ollama/gemma4:31b-cloud']` and `agent models missing from the tiers: [('nvidia', 'nvidia/nemotron-3.5-lightning-30b-a3b')]`. The routes themselves were fine; the bookkeeping was not. `nemotron-3-nano:30b` and `gemma4:31b` had been put into the tiers before the free-plan set and the tool-calling gate learned about them; `gemma4:31b-cloud` was in the gate but its evidence file used bare model names, so the fixture writer skipped it; and the NVIDIA Lightning 30B was in the agent rotation but in no tier at all. All four were re-probed **live** on 2026-11-03 through the delegate's own request builder (`workspace/subagent_tiers/research/reprobe_gap.py`) — each answered without the Ollama 402 refusal and with a real tool call — and the registries now match that evidence instead of a stale claim.

### Security
- **A pasted OAuth client secret no longer sits in a tracked file** (`data/cli_history`, `.gitignore`): the interactive prompt history (`core/input_handler.py`) records what was typed at the permission gate, so the Google OAuth client ID and secret that were pasted during the plugin setup ended up in `data/cli_history` — a file that was **tracked in git** and would have gone out to the remote with the next commit. That file is runtime state, not source: it is now ignored and untracked, the credential has been stripped from it, and the prompt history it keeps is a local convenience only.

### Added
- **The AI pings you when it is waiting for you** (`core/notifier.py`, `core/permissions.py`, `core/tools.py`, `core/interface.py`): three moments stop the runtime and wait for a human — the permission gate ("allow all listed actions? [y/n]"), the `confirm` tool and the `ask_user` tool. On a phone the terminal is normally in the background, so those prompts were invisible: the runtime sat on `input()` and said nothing, and the user found out minutes later that the AI had been waiting all along. With `notify: true` each of them pushes a system notification, and each kind gets its own title — "Termux-AI: Permission needed" (every command in the batch and the reason for it), "Termux-AI: Confirmation needed" (the question and what Enter answers) and "Termux-AI: Question" (the question and its options). The flag is read from `config.json` at every prompt, so `/notify false` takes effect on the very next question. The notifier never prints and never raises: a missing Termux:API package means the notification is skipped, not that the question is. The plumbing is verified against the **real** device, not only against a stub: `workspace/checks/check_notify_live.py` drives the actual permission gate, `confirm` and `ask_user` and asserts that the three notifications really reach the shade, that their bodies carry the question/command/options, and that they never leak into the terminal line (19/19).
- **`/notify true | false | status`** (`core/interface.py`): the command used to flip the flag silently — no output at all, so it looked like it had been ignored. It now confirms what it did, reports the current state on request, and sends one test notification when switched on, so the plumbing is proved instead of assumed.
- **One shape for `config.json`** (`core/app_config.py`, `core/permissions.py`, `core/tools.py`, `core/interface.py`): three modules each carried their own copy of the default configuration and they had drifted — the copies in `permissions.py` and `tools.sleep_mode` never learned about the `notify` flag, so a `config.json` written by either of them was missing a key the interface expected, and the interface silently patched it back on the next load. The canonical set now lives in one place (`core/app_config.py`); the I/O stays with whoever needs it, because `display_state.py` persists `show_details` on its own schedule and must not be clobbered by a shared writer.

### Fixed
- **The expanded tool view no longer hides a call's arguments** (`core/llm_client.py`): the expanded display (`Ctrl+O`, `/expand`) showed every argument of a call — except the ones passed as a separate list, which came out blank: `find_replace` lost its `case_sensitive` flag, and a handful of other calls showed a bare tag with nothing under it. The argument printer now walks every parameter of the call, so the expanded view really is the whole call; an audit over all 82 tools (`workspace/audit/audit_expand.py`) reports 0 calls with invisible arguments. A refused call (a plugin that is switched off) and an unknown tool now show what was attempted too — otherwise the user could not tell what the model had tried, or why it had been turned down.
- **A delegated worker's thinking reaches the screen** (`core/tools.py`): the sub-AI's reasoning was logged but not displayed when the provider reported it as `reasoning_details` (a list of typed blocks) instead of the plain `reasoning` field — which is what OpenRouter does. The delegation path now flattens both shapes, so the worker's reasoning shows in the expanded view instead of vanishing.
- **A diagnosis no longer stalls or throws** (`core/tools.py`, `tools/wrapper_termux_battery_status.py`, `tools/wrapper_termux_wifi_scaninfo.py`): `run_diagnosis` collected six device checks in parallel and gave up after ten seconds — but the collector's own cleanup step could itself raise (`TimeoutError`), and the executor it was built on waited for every wedged command to finish before returning. On a phone where the battery broadcast and the Wi-Fi query each take eight seconds, the tool therefore either crashed or took half a minute, while the two checks it retried were the very commands that had just timed out. The snapshot is bounded twice over now: a check that timed out is reported as a timeout instead of being run a second time, the network check asks the connected access point first (a full scan is slower and only says what is nearby), and the collector returns what it has — a dict, always — instead of raising. Measured on the device: 6-12s, inside the 15s the tool contract asks for.
- **The WhatsApp plugin no longer talks in the middle of a chat** (`core/whatsapp_manager.py`, `core/plugin_runtime.py`, `core/interface.py`, `core/tools.py`): three things the plugin said on its own are gone. (1) **The pairing QR.** The gateway prints the pairing code — a live secret, whoever scans it gets read/write access to the owner's account — and whatsapp-web.js rotates it every few seconds while the WebSocket replays the current status (code included) on every reconnect. The manager rendered it into the terminal every single time, so an unpaired device was buried under QR art for the whole session. It is now **captured** instead of printed and drawn only when the user asks for it. (2) **"Connected and ready. My number: …".** The `SYSTEM_READY` event printed the owner's number into the middle of the chat on every start; it is now silent, the number is still kept for the group-mention check, and `/plugin status whatsapp` reports "LINKED" on request. (3) The `Status: …` chatter on every state change is gone too. A live check drives the real manager against a real WebSocket server that replays all three events and asserts that the terminal stays empty (`workspace/checks/check_quiet_whatsapp.py`, 10/10).
- **Asking for the QR on a linked session resets the plugin instead of pretending** (`core/plugin_runtime.py`, `core/interface.py`, `core/tools.py`): `/plugin setup whatsapp` (and `manage_plugin(action='setup', plugin='whatsapp')`) is now the pairing path. When the session is **not** linked, the gateway is started and the code is put on the screen once. When it **is** already linked, a pairing code is only wanted for a re-link — so the gateway is killed (every `bot.js` process serving this checkout, not just the one this session started) and the plugin is switched off, and the user is told so. The decision waits for the gateway to report a *decided* pairing state: the HTTP port opens long before the WhatsApp engine has booted, and deciding during `INITIALIZING` would hand out a code for a session that is in fact already linked.
- **The entry point no longer starts a second gateway** (`core/__main__.py`): `python core` spawned its own `node bot` and printed the gateway's stdout into the terminal — the rotating pairing code went straight into the chat with it. It also *blocked* the chat loop until "System Connected!" appeared, so an unpaired device never reached the prompt, and it ran a second gateway next to the one the plugin runtime starts (two listeners on one WhatsApp session means every incoming message is handled twice). The runtime owns the gateway now; the entry point only starts the chat.
- **A disabled plugin stops listening** (`core/whatsapp_manager.py`): the WebSocket listener had no stop path. `/plugin disable whatsapp` stopped the gateway but left the listener thread alive, reconnecting every five seconds — so a gateway that came back later was picked up by a plugin the user had switched off, and every incoming message was handled again. The listener is now closed with the gateway.

### Added
- **Enabling a plugin now makes it *work*, not just switch a flag** (`core/plugin_runtime.py`, `core/plugin_manager.py`, `core/whatsapp_manager.py`, `core/interface.py`, `core/tools.py`): `/plugin enable whatsapp` used to write `"enabled": true` into `config.json` and stop there. The assistant was then handed the WhatsApp tools — `send_whatsapp_message` and its seventeen siblings — while the Termux-WP node gateway (`bot.js`, the process that actually owns the WhatsApp session) was still down, so **every single call failed with "connection refused"** until somebody remembered to start the gateway by hand in a second terminal. A new runtime layer (`core/plugin_runtime.py`) owns that difference: enabling a plugin now *starts what the plugin needs to run*, disabling it stops it again, and the plugin's tools enter the assistant's tool context in the very same turn — no restart, no repeat of the request. The plugin manager tool (`manage_plugin`) stays in the tool list whatever the plugins are doing (`ALWAYS_AVAILABLE_TOOLS`), because it is the only way the assistant can switch a plugin on in the first place.
- **A gateway that dies is restarted instead of leaving the plugin dead** (`core/whatsapp_manager.py`): the WhatsApp Web engine runs headless Chromium against a profile directory, and on Termux that Chromium regularly gives up during initialisation — taking the whole node gateway with it. Nothing used to restart it, so every WhatsApp tool answered "connection refused" until a human intervened. A watchdog now watches the gateway and brings it back with a growing delay (5s, 10s, 15s … capped at a minute), and it keeps retrying even when a restart attempt *fails* — that case used to leave the plugin down with no process left to watch.
- **An orphaned browser no longer blocks the next gateway** (`core/whatsapp_manager.py`, `Termux-WP/bot.js`): when the gateway died, its Chromium could survive and keep the WhatsApp profile locked. The next gateway then refused to start with *"The browser is already running for …"*, and the plugin stayed broken until somebody killed the orphan by hand. The gateway now closes its browser when the engine fails, and the plugin clears a browser that holds the profile while its gateway is gone before starting a new one. A browser that still belongs to a running gateway is left alone.
- **"Ready" means ready** (`core/whatsapp_manager.py`): the HTTP port opens *before* the WhatsApp Web engine has finished initialising, so the old check called a gateway "started" while it was already on its way out. The start now waits for the process to survive a short settle window, and a gateway that dies during it is reported as a failure — with the actual reason out of `bot_output.log`, not a bare "connection refused".
- **The assistant is told the truth about a broken runtime** (`core/interface.py`, `core/tools.py`): `/plugin enable` no longer prints "Its 17 tools are now in my tool context — say 'try again' and I can use them right away" when the runtime failed to start. It now names the reason ("node is not installed", "Termux-WP is missing", "the gateway did not open port 3000") and says that the tools are advertised but will fail until the runtime is up. `/plugin setup whatsapp` goes through the same runtime-aware activation as `/plugin enable`, so it starts the gateway too instead of only flipping the flag.
- **The session no longer dies on a device without Termux-WP** (`core/interface.py`): the startup path called `whatsapp_manager.ensure_running()` through a name that only existed when the WhatsApp library happened to import cleanly — on a device without the Termux-WP checkout that name was never bound, and the chat loop died with a `NameError` at startup. The manager is now imported explicitly and its absence is reported as a message.
- **A real-path integration test for plugin activation** (`tests/test_plugin_runtime_integration.py`): every test for plugin activation monkeypatched the runtime, so the suite stayed green even when the actual `bot.js` start path was broken. The new test captures the real runtime functions before the fixture stubs them, starts a real gateway, proves the port opens and the tool context gains the WhatsApp tools, and stops the process again — it skips (rather than fails) when the device has no Termux-WP, no `node`, or a gateway that the user started by hand.
- **A second session is called out instead of answering twice** (`core/interface.py`): two Termux-AI sessions share one WhatsApp gateway, and each opens its own WebSocket listener to it — every incoming message was then handled twice and the busy auto-reply answered twice. The sessions cannot see each other in memory, so the new session now finds the others in the process table and says so at startup.

### Fixed
- **The browser tool no longer makes a model guess where a button is** (`core/tools.py`): a click used to be aimed either by raw viewport coordinates or by a CSS selector, and in both cases the model had to *invent* something — pixels, or a selector like `#submit` that may or may not exist. Every guess that missed cost a tool round, so the first clicks of a task were spent finding out where the buttons were. The page itself knows, so the page is now asked: a new **`find`** action lists every visible button, link and form field with **the label a human would read** ("Submit"), a **ready-to-use CSS selector** that is unique on that page, and its live rectangle. A click can then be aimed by `text` ("the button labelled Submit"), by `index` (the 1-based number from the listing) or by `selector` — and the position is resolved against the live DOM *at the moment of the click*, so the element is scrolled into view and clicked at its centre. A `label` does the same for a form field ("Email"). A failed lookup now answers with what **is** on the page ("no element is labelled 'Purchase'. available: [1] button "Submit" (#submit); [2] …"), which turns a blind guess into a one-step recovery instead of another guess; an ambiguous label ("Save", twice) is refused rather than guessed, because clicking the wrong button is worse than asking once more. The no-JS fallback scraper understands `find` and label clicks as well, and the tool descriptions now tell the model to run `find` instead of guessing coordinates.
- **The sub-agent is chosen by intelligence level, not by model id** (`core/tools.py` / `core/models.py`): `delegate_subtask` now takes `intelligence` (`high` | `medium` | `low`) instead of `model`, and the routing table lives in `core/models.py` as `SUBAGENT_TIERS`. The old `model` parameter handed the caller a list of slugs that went stale, and the `max_tokens` parameter capped the report at a number nobody could justify — a long analysis was cut off in the middle with no way to ask for more. The tiers are ordered by measured capability, not by name: **high** holds the strongest free reasoning models (Gemini 3.8 Flash, MiniMax M3.1 Flash, Qwen3.8-27B, Nemotron 3.5 Super VL, Nemotron 3 Ultra 550B, Mistral Large 4, Step 5), **medium** the balanced workhorses (GPT-OSS 120B, Nemotron 3 Super, Poolside Laguna XS, Gemma 4 31B, Dots 3 Note Preview), **low** the cheap and fast end (Gemini 2.5 Flash, Gemini Flash-Lite, Gemma 4, North Mini Code, LFM 2.5, Flint). Every model in the registry was verified live to accept a `tools` payload and answer with a tool call; the ranking uses the published Artificial Analysis indices and the vendor model cards, and `model_supports_tools()` keeps the gate honest.
- **The sub-agent pool is free-only, and that is now enforced** (`core/models.py`): Termux-AI is built for free AI, so every route in the chat rotation, the agent rotation and the sub-agent tiers must be servable without paid credits. The paid models that used to sit in those lists — OpenRouter's Gemini 4 Argon, Kimi K3 / K3.1 Pro, GLM-5.3, MiniMax M3.1 Flash and DeepSeek V4.1 Flash, plus Ollama's minimax-m3, glm-5.3 / glm-5.2, kimi-k3 and deepseek-v4.1-flash — were removed after a live probe showed them refusing with HTTP 402 ("this model is not included in your free usage"). The rule is now machine-checked instead of a convention: `is_free_route()` decides a route by the provider's own signal (an OpenRouter slug is free only with the catalogue's `:free` marker, a Google model only in the Flash/Lite/Gemma families, an Ollama model only on the account's Free plan), `PAID_MODEL_DENYLIST` records the routes that were verified to refuse, and `free_route_violations()` reports any paid route that slips back into a registry — the test suite fails on it.
- **No output cap is imposed on the sub-agent** (`core/tools.py`): the tool sends no `max_tokens` at all for providers that answer until they are done (Google, NVIDIA, Ollama — verified with a long-answer probe), so a report is never cut in the middle. Groq (which silently truncates at 3072 tokens without the field) and OpenRouter (whose balance check rejects a request without a number) keep an explicit ceiling, and that ceiling is *lowered* — never guessed — when the account says it cannot afford it: the 402 answer "requires more credits, or fewer max_tokens" halves the budget and retries the same route. A truncated answer is never thrown away: the partial content is carried into the next model with a "continue" instruction.
- **A delegated worker gets a toolkit, not the whole arsenal** (`core/tools.py`): advertising every tool of the system (73 schemas, ~46 KB of JSON) pushed several providers over their request-size limit before the sub-AI even read the task — Groq answered "413 Request too large … on tokens per minute". The sub-AI now gets a curated core set (shell, read_file, write_file, find_replace, list_directory, search_files, search_in_files, index_files, browse_web, http_request, get_datetime) unless the caller names a different one, and a tool result that comes back too large is shortened before it is fed back into the worker's context.
- **The tier fallback ladder only goes down** (`core/models.py`): a `high` task that nobody can serve degrades to `medium` and then `low`, a `medium` task degrades to `low`, and a `low` task stays `low`. It never climbs: a "medium" request must not be served by a frontier model the caller did not ask for.

### Added
- **Context overflow no longer throws the work away** (`core/context_compressor.py`): when the provider reports that the context does not fit, the old recovery was to shrink `max_tokens` and move on to the next model — reasonable for a model that has just started working, wrong for work that runs for days, where the thread of the task is worth more than the model that happened to be running. The oldest passes of the active context are now **compressed** instead: their reasoning details, tool-call arguments and raw tool outputs are replaced by a dense digest, and the discarded text is **archived on disk** (`logs/context_archive.jsonl`) under a stable id. A marker left in the conversation names that id, so the model can pull the raw content back, check how much work was already done, and continue from there. Compression is progressive (digest → compact → stub) and deliberately **partial**: it starts with the most distant passes and stops as soon as the payload fits, so the recent work and the live turn stay raw. The system prompt, the recent turns and the prompt being answered are never reduced to a stub, and a pass is only compressed when every tool call in it has its matching result — a half-compressed pass would leave orphan tool messages that providers reject.
- **`retrieve_archive` and `list_archives` tools** (`core/tools.py`): the model reads an archived segment back by id (`retrieve_archive('A3')`, paged with `offset`/`limit` because a segment can be far larger than the window that triggered the compression) and lists every archived segment with its id and size. The system prompt now tells the model that a digest is a summary and the archive is the evidence.
- **A real OAuth layer for the Google plugins** (`core/google_oauth.py`): Gmail, Google Calendar and Google Drive previously existed only as *placeholder* names — the plugin manager knew a plugin called `gmail` was switched on, but nothing knew how to obtain access to a mailbox. The new module owns the whole "connect the account" story: it stores the OAuth client credentials the user creates once in Google Cloud Console (`config/google_oauth.json`, mode 0600), stores per-service access+refresh tokens (`data/google_tokens/<service>.json`, mode 0600), runs the consent flow, refreshes access tokens transparently, and reports the current state.
- **Two consent flows, because the client type decides**: the **browser redirect with a local callback** (a throwaway `127.0.0.1` server catching Google's redirect) is the flow a **Desktop app** client uses, and the one that can request the Gmail/Calendar/Drive scopes. The **device-code flow** (the user opens a URL on any device, types a short code and the app polls until the token arrives) belongs to a **TVs and Limited Input devices** client and accepts only a small allowlist of scopes. Both use PKCE, which Google requires for installed applications; the usable one is picked automatically.
- **A real Google API client** (`core/google_api.py`, 17 operations): Gmail list/read/send/labels/create-label/delete, Calendar list-calendars/list/create/update/delete events, Drive list/upload/download/delete/create-folder/share. Every call goes through `get_access_token()`, which refreshes an about-to-expire token silently, so callers never think about token lifetime.
- **`/plugin` command** (`core/interface.py`): `list`, `status`, `enable`, `disable`, `setup` and `disconnect`. Enabling an account plugin no longer just flips a flag — it starts the permission request immediately and prints the URL to approve, because a switched-on plugin that cannot work is exactly the confusing state this replaces.
- **`manage_plugin` tool** (`core/tools.py`): lets the model handle "turn on Gmail" / "is Calendar connected?" without the user remembering a slash command. Actions `list`, `status`, `enable`, `disable`, `setup`, `finish`, `disconnect`. Because a *tool call* cannot sit and wait minutes for a browser click the way `/plugin setup` does, the consent flow is split: `setup` returns the URL immediately and `finish` collects the result afterwards within a bounded wait. It is deliberately **not** offered to a delegated sub-AI, since enabling a plugin mutates shared configuration.
- **A startup notice for half-configured plugins** (`core/interface.py`): a Google plugin can be switched on in `config.json` without the account ever having granted access. The session now says so at start-up, prints the exact command, and offers to run the setup when someone is actually at the terminal. In a piped or scripted session it prints the notice without prompting, so it can never swallow the next input line.

### Added
- **NVIDIA free image generation** (`core/tools.py`): `generate_image()` now supports NVIDIA's Visual Design (FLUX) endpoints alongside Google Gemini. NVIDIA serves image inference from a *different* host than its chat API — `POST https://ai.api.nvidia.com/v1/genai/{model}` — reached through the new `nvidia-images` provider entry in `core/models.py` `PROVIDERS`. Registered models:
  - `black-forest-labs/flux-3-image-klein` — newest general model, `cfg_scale` 1–20, `steps` 1–50
  - `black-forest-labs/flux.2-klein-4b` — fastest (4-step distilled), `cfg_scale` fixed at 1, `steps` 1–4
  - `black-forest-labs/flux.1-dev` — highest fidelity, `cfg_scale` >1 and ≤9, `steps` 5–100
  - Response shape is `{"artifacts": [{"base64": "<JPEG>", "finishReason": "SUCCESS", "seed": N}]}`.
- **Image model registry** (`core/models.py`): new `IMAGE_MODEL_SLOTS` list holding every image-generation model (Google + NVIDIA) with its provider, API kind and live parameter envelope. It is deliberately separate from `MODEL_SLOTS` / `AGENT_MODEL_SLOTS`, which drive the chat-completions rotation and contain text models only.
- **`generate_image()` parameters**: the tool gained `provider` (`auto` | `google` | `nvidia`), `model` (pin an exact model id), `width`, `height`, `seed`, `steps`, `cfg_scale` and `negative_prompt`. `provider="auto"` keeps Google as the first attempt and falls back to NVIDIA. An explicitly pinned `model` overrides the provider filter.
- **The full NVIDIA image catalogue** (`core/models.py`): every model from NVIDIA's image catalogue is now registered, with its parameter envelope read off the live service. The two new hosted models are `black-forest-labs/flux.1-schnell` (`cfg_scale` ≥ 0, `steps` ≤ 4) and `black-forest-labs/flux.1-kontext-dev` (an image-*editing* model: `cfg_scale` > 1 and ≤ 9, `steps` 5–100, `aspect_ratio` from a fixed set of seventeen literals). Four catalogue models — `qwen/qwen-image`, `qwen/qwen-image-edit`, `nvidia/qwen-image-edit-nvpcb-ovsl2sl` and `stabilityai/stable-diffusion-3.5-large` — are **self-hosted NIMs**: they are listed for completeness but return HTTP 404 from the hosted API, so they carry `hosted_available: False` and are skipped by the rotation instead of burning a request.
- **Per-model size grids** (`core/models.py` / `core/tools.py`): the accepted width/height literals differ per model — FLUX.3 and FLUX.2 Klein take 512–1568 in steps of 16, FLUX.1 takes 768–1344 in steps of 64, and Kontext has its own seventeen values from 672 to 1568. The registry now records the grid per slot and the request builder snaps onto it, instead of using one shared grid for every model.
- **Vision registry** (`core/models.py`): new `VISION_CAPABLE_MODELS` and `model_supports_vision()` listing the models whose chat endpoint accepts an image. Every entry was verified by sending a real PNG and checking the request was accepted. Models that were *rejected* are absent, and the rejection is the evidence: NVIDIA's `nemotron-3-ultra` / `nemotron-3.5-lightning` answer "multimodal processing is not enabled", Ollama's `gpt-oss` / `nemotron-3-ultra` answer "does not support image input", and Groq requires `content` to be a plain string. `nvidia/nemotron-3.5-super-vl-120b-a12b` was added to the agent rotation — it is a free serverless vision-language endpoint.
- **Persistent browser sessions** (`core/tools.py`): new `browser` tool with `action` = `open` | `act` | `navigate` | `screenshot` | `state` | `close` | `list`. `open` launches a real Chromium and returns a short session id (`b1`, `b2`, …); every later call passes that id back and works on the *same live page* — its scroll position, cookies and half-filled forms intact — so the model can click through a flow over several calls. `close` shuts the browser down and frees its profile. Sessions idle for five minutes are reaped, and an `atexit` hook closes them all on shutdown.
- **Browser interaction** (`core/tools.py`): the action list grew `scroll` (by a delta, to a position, or to the top/bottom), `press` (real key events — `Enter`, `Tab`, `Escape`, the arrows) and `select` (choose an option and fire its `change` event). Reading a form control back now reports its **value**, not its text content — an `<input>` has no text, so the previous extraction returned nothing for a field the model had just typed into.
- **Screenshots and image seeing** (`core/tools.py` / `core/llm_client.py`): `browse_web` and the `browser` tool now capture the viewport and attach the picture to the reply, so a multimodal model can actually look at the page. The picture is captured as JPEG, downscaled to 1024×1024 and queued as an attachment; the request builder inlines it as a data URI only for a model that can see images, and at most three images go out per request. A model that cannot see images gets a short note instead of a picture, and a provider that rejects the image payload is retried once without it rather than losing the whole model slot.
- **The picture travels in a user message** (`core/llm_client.py`): the image part is attached to a *user* message that follows the tool result, not to the tool message itself. Google rejects an image part inside a tool message ("Invalid content part type: image_url"), while a following user message works on every provider that can see images.
- **Automatic switch to a vision-capable model** (`core/llm_client.py`): when a tool captures a picture but the running model cannot see images, the turn moves to a configured vision model instead of the model receiving a note about a picture it will never see. The switch happens at most once per turn.

### Fixed
- **The model's working trace no longer leaks into the answer** (`core/llm_client.py`): the reply the interface prints after "AI >" / "Agent AI >" was stitched from *every* assistant message of the turn — including the narration a model writes next to its tool calls ("Let me look at the fallback extraction code first."). The result was an answer that opened with a paragraph of the model's running commentary, glued to the first sentence without a line break (visible in `workspace/example.txt`). `_stitch_assistant_turns()` is replaced by `_split_assistant_turns()`, which separates the narration from the answer: an assistant message that carries tool calls is working trace, everything else is answer material. The trace is printed in its own labelled block — `[Working trace]`, collapsed by default and expanded with Ctrl+O, next to the provider's native reasoning — and never inside the answer the user reads. A length-truncated answer plus its continuation still arrive as one answer, and a turn that produced only narration still says something instead of "[EMPTY RESPONSE]".
- **The context overflow is now handled by the API's answer, not by a local guess** (`core/llm_client.py` / `core/models.py` / `core/context_compressor.py`): the registry of "context limits per model" (`CONTEXT_WINDOWS`, `PROVIDER_CONTEXT_WINDOWS`, `get_context_window()`) was a guess about endpoints that enforce something else — it claimed 256K for `deepseek-ai/deepseek-v4.1-flash`, whose endpoint answers *"This model's maximum context length is 8192 tokens"*. Because the registry said the history fit, the request went out unchanged, the provider refused it, and the runtime retried the same hopeless request ten times instead of compressing the context it already had. The registry is **gone**, together with the proactive pre-flight compression it drove: the payload is sent as it is, and the compression runs **when the provider reports the context limit** — the oldest passes are compressed into a digest, the raw text is archived under a stable id, and the *same* model is retried. The window the provider states in its error ("maximum context length is 8192 tokens") is parsed and used as the compression budget, with the tool catalogue and the output cap taken off the top, and the output cap is clamped into that window so a slot cannot ask for more output tokens than the model has room for in total. A gateway that answers an oversized body with **405 / 413 / 422 / 431** and no readable message also triggers the compression; a quota, auth or rate-limit failure keeps its own handling whatever the status says. When the tool catalogue alone does not fit the stated window it cannot be compressed at all, so the model is skipped after one honest attempt instead of burning ten retries.
- **The "reduce max_tokens" fallback actually reduced it** (`core/llm_client.py`): the recovery path wrote the halved cap into the request-local `slot_max_tokens` dict but left the local variable alone — and the retry is sent from that same loop, so the request went out with the *same* output cap it had just failed with. The local value is updated now.
- **`extract_html` is no longer swallowed by the dispatcher** (`core/llm_client.py`): the `browse_web` and `browser` tool schemas advertise an `extract_html` flag, and the tools implement it — but the dispatch routes never forwarded the argument, so a model asking for the raw page HTML got the usual markdown extract instead and had no way to tell.
- **A context error no longer degrades a model for the rest of the process** (`core/llm_client.py`): the old recovery path did `slot_cfg["max_tokens"] = max_tok // 2` — and `slot_cfg` is the *shared* `MODEL_SLOTS` / `AGENT_MODEL_SLOTS` dictionary. One over-long prompt therefore permanently halved that model's output cap for every later request in the session, and the halving was never restored. The reduction is now request-local (`slot_max_tokens`), and it happens only after compression has already been tried.
- **"Rate limit exceeded" is no longer read as a context error** (`core/llm_client.py`): `_is_context_error()` matched the bare words "context", "exceed" and "window" anywhere in an error message, so a rate-limit failure ("429 rate limit exceeded") was classified as a prompt-too-large error and sent the runtime into a max_tokens halving loop instead of the key-rotation path it belonged to. The matcher now looks for the phrasings providers actually use for a prompt that does not fit ("maximum context length", "context_length_exceeded", "input length and max_tokens exceed context window", "prompt is too long", …) plus HTTP 413.
- **The Google OAuth setup can actually succeed now** (`core/google_oauth.py`): the setup guide told the user to create a **"TVs and Limited Input devices"** OAuth client — precisely the type that cannot work here. Google's device-code endpoint answers such a client with `invalid_scope` ("Invalid device flow scope: …gmail.modify"), because that flow supports only a small allowlist of scopes and Gmail, Calendar and Drive are not on it; Google's loopback-migration guide then explains that the local redirect is kept for **desktop clients only**, so the browser showed the user *"Access blocked: Termux-AI's request is invalid"*. The guide now asks for a **Desktop app** client (what Google's own Desktop-app documentation prescribes — local redirect plus PKCE), the flow that actually works is selected automatically, and a client of the wrong type is named in plain language instead of producing Google's wall.
- **The setup guide is colourised and carries a URL for every step** (`core/google_oauth.py`): `client_setup_instructions()` lists the consent screen, all three API library pages, the client page and the reference documentation — each with the link to open — and says in colour that the application type must be *Desktop app* and that the TV type must not be picked.
- **The `/plugin` hints named a command that did not exist**: every hint said `/plugin gmail setup`, but the parser only understood `/plugin setup gmail`. All hints now use the documented order, and the parser accepts both spellings (`/plugin setup gmail` and `/plugin gmail setup`).
- **A blocked consent attempt is explained instead of swallowed** (`core/google_oauth.py`): the consent URL is now checked with Google *before* the user is sent to it, so a client/redirect combination Google rejects is reported with the reason and the fix (`stage="blocked"`) instead of a bare failure. A consent approved on another device can also be completed by pasting the redirect URL — via `/plugin setup <name>` or `manage_plugin(action="finish", code=…)`.
- **Turning a Google plugin on no longer silently does nothing**: the three Google entries were names without behaviour — enabling `gmail` flipped a boolean, changed nothing visible, and left the user with no way to grant access. Enabling one now starts the permission request and shows the URL; the state is visible in `/plugin list` as `NEEDS SETUP` / `NO OAUTH CLIENT` / `CONNECTED (account)`.
- **An account plugin's tools are only advertised once the account is actually connected** (`core/plugin_manager.py`): `is_tool_allowed()` requires *enabled and connected*, so the model is never offered a Gmail tool that is guaranteed to fail. A call attempted anyway returns an explicit error naming the command to run instead of a bare failure.
- **Google credentials are gated in every permission mode, including autonomous** (`core/permissions.py`): `config/google_oauth.json` (client secret), `data/google_tokens/` (refresh tokens) and `data/google_pending_auth.json` (a live PKCE verifier) join `config/api.keys` as protected paths. The matcher is word-boundary aware, so `mygoogle_tokens` is not mistaken for the real directory.
- **The consent wait no longer measures time with the wall clock** (`core/google_oauth.py`): CLOCK_REALTIME on this device intermittently runs 38–97s *ahead* of CLOCK_MONOTONIC (Android suspend / time sync), which would end a device-flow wait the moment it began. The wait now uses `time.monotonic()`, and the bounded `finish` call sleeps only until its deadline rather than past it.
- **NVIDIA image request envelopes**: the published NVIDIA reference pages disagree with the running API, so every parameter bound was verified live rather than copied from the docs — the model slug uses a hyphen (`flux-3-image-klein`, not `flux.3-image-klein`), `mode` accepts only `"t2i"`/`"i2i"`, `flux.2-klein-4b` rejects a `mode` key outright, `flux.1-dev` returns a 500 when one is sent, and every model enforces a 1,062,400-pixel budget. The request builder clamps every knob to the model's real envelope and never sends `mode`.
- **`flux.1-schnell` and `flux.1-dev` are no longer hard-coded out of the rotation**: both endpoints are currently unhealthy on NVIDIA's free tier (a 504 gateway timeout and a 500), but they are registered like any other model and skipped by the endpoint-health cache while they are down. They come back automatically once NVIDIA restores them, instead of having to be re-added by hand.
- **`generate_image()` base URLs** are now resolved from `PROVIDERS` at call time rather than at import time, so an endpoint fix propagates without a restart.
- **Generated images are saved with an extension that matches their bytes**: NVIDIA's FLUX endpoints return JPEG while Gemini returns PNG, but every image was written as `.png`. Android then received a `.png` name for JPEG data, so `termux-open` and the share sheet picked the wrong MIME type and the file could render as broken. The saved path is now derived from the payload's magic bytes (`.png` / `.jpg` / `.webp`).
- **A hung NVIDIA endpoint no longer stalls the whole rotation**: the per-request timeout dropped from 180s to 90s, and a transport-level failure (read timeout, connection reset) now moves on to the next model instead of re-trying the same dead endpoint with the next key. A hung endpoint previously cost *keys × timeout* (6 minutes with two keys) before any fallback model was even tried. HTTP-level failures (401/403/429) still rotate keys, because those really are key-specific.
- **Content-filter rejections are reported plainly**: when every NVIDIA model returns `finishReason=CONTENT_FILTERED`, the error now states that the prompt was rejected by the safety filter and suggests rephrasing, instead of showing a wall of near-identical per-model lines that left the cause unclear.
- **A dead NVIDIA endpoint is remembered instead of retried forever**: an endpoint that fails at the transport level is skipped by the automatic rotation for a while (the cooldown grows with the number of consecutive failures), so the second call costs 0s instead of another full timeout. An explicitly pinned model is always tried — the caller asked for it by name and it may have recovered.
- **The NVIDIA request timeout dropped from 90s to 60s**: the healthy endpoints answer in 2–15s, so 60s is a comfortable margin and a dead endpoint costs less while the rotation moves on.
- **The browser profile no longer assumes `/tmp` is writable**: the Chromium profile directory and the screenshots live under `workspace/` now. `/tmp` is not writable on Termux and does not exist on Windows, so the old hardcoded path was not portable.
- **Screenshots are pruned**: only the 60 most recent are kept, because they are only useful for the turn that captured them and would otherwise fill the device storage.
- **Chromium startup no longer fails on an empty tab list**: the DevTools tab list can be briefly empty right after the debugging port opens, which used to abort the launch with "Chrome started but has no tabs". The target list is now polled for up to 12s, and a real `page` target is preferred over `devtools`/background entries.

- **Structural shell parser** (`core/shell_parse.py`): New module that parses shell commands structurally and returns the source text of every simple command it contains — including those nested inside `for`/`while`/`until`/`if`/`case` blocks, `{ }` groups, subshells, function bodies, and `$( )` / backtick substitutions. On expiry the whole process tree is killed via `killpg` + a `/proc` session sweep.
- **Chain-wide timeout ceiling**: The `shell` tool gained a `total_timeout` parameter — a ceiling for the **whole chain**, independent of how many stages it has. Both are now reported distinctly: a stage timeout says so, a chain ceiling says "chain-wide limit".

### Changed
- **Shell timeout semantics**: The `shell` tool's `timeout` is now applied per command in a chain rather than to the chain as a whole, and every process spawned by a command is terminated with it. The tool description and the dispatch default (`30` instead of `0`) were updated to match.
- **Permission gate: structural instead of textual**: The gate used to cut a command at every `;`, `&&`, `||` and newline, which tore compound blocks apart — the cut landed inside the block and the segment's command word became a shell keyword (`do`, `then`, …) instead of the command that runs. It now parses the command and checks every simple command it contains.
- **Single permission-module instance**: `core/tools.py` imported the gate as a top-level `permissions` module while three other call sites used `from core import permissions`, so the running app loaded **two** independent copies of the same file with separate module state. The import is now consistent.
- **Monotonic clocks for durations and deadlines**: `core/tools.py` (port/CDP wait loops) and `orchestration/worker.py` now measure elapsed time with `time.monotonic()` instead of `time.time()`. The wall clock can jump on Android (system suspend / time sync), which made deadlines fire early and inflated reported durations.
- **Provider URLs**: `ask_ai_simple()` and `delegate_subtask()` read their base URL from `core/models.py` `PROVIDERS` instead of hardcoding them, so provider fixes propagate.
- **Tab completion**: Now only offers commands that actually exist.

### Fixed
- **Permission gate blind to compound blocks**: `for i in 1 2 3; do rm -rf $HOME/x; done`, `if true; then rm -rf /tmp/y; fi`, `while read l; do rm -rf $l; done`, `case $x in a) rm -rf /tmp/c ;; esac`, `{ rm -rf /tmp/g; }` and `( rm -rf /tmp/s )` all bypassed the gate. The destructive command inside the block is now inspected, and the gate reports the offending command rather than the keyword.
- **Four more permission bypasses of the same class**: Leading `NAME=value` assignments hid the command (`FOO=1 rm -rf /tmp/env`); wrapper commands ran another command behind the gate (`command rm -rf …`, `env FOO=1 rm -rf …`, `xargs rm -rf …`, `nohup rm -rf …`, `timeout 30 rm -rf …`); command substitutions executed unchecked (`echo $(rm -rf /tmp/x)`, `` echo `rm -rf /tmp/x` ``); and the right-hand side of a pipe or background job was never inspected (`ls | tee /tmp/out`, `sleep 1 & rm -rf /tmp/x`).
- **`$VAR` in a path was never resolved**: `rm -rf $HOME/x` looked like a relative path inside the project root and was waved through; paths are now expanded before the location check.
- **`api.keys` could be smuggled past the gate**: The reference was only looked for in the individual segments, so `for f in config/api.keys; do cat $f; done` slipped through. The reference is now checked against the whole command, in every mode.
- **Inline interpreter code was only pattern-matched**: `bash -c "rm /tmp/x"` passed because the pattern list only looked for the recursive form; the inline code is now parsed and each command in it is checked.
- **Parser could be used as a denial-of-service vector**: Every nesting level re-parsed the text inside it, so a deeply nested command substitution was quadratic in the length of the command (7s for 3,200 levels). Delimiters are now matched in a single pass and substitution depth is limited — 246ms for the same input.
- **Orphaned shell processes**: On timeout the old `shell()` called `Popen.kill()`, which signalled only the `bash` process — every process it spawned survived, reparented to init, burning battery and still writing files. The whole tree (process group + a `/proc` session sweep) is now terminated.
- **Shell tool hanging past its timeout**: The old `shell()` called `communicate()` after the kill, which blocks until every pipe holder exits, so a grandchild could keep the tool call alive for minutes. Output is now read on background threads and the call always returns on time.
- **A stage timeout could be silently swallowed**: GNU `timeout` exits with 124, but the chain's exit status hid it — `sleep 300 || echo recovered`, `sleep 300 ; echo after` and `sleep 300 | cat` all finished with status 0, so the tool reported success for a command it had actually killed. A DEBUG trap now observes every command's status (and `${PIPESTATUS[0]}` for the left stage of a pipeline), so a timeout is reported no matter which operator follows it.
- **Orchestration worker could hang forever**: `orchestration/worker.py` ran tasks with `subprocess.run()` and no timeout; a stuck command blocked the orchestrator indefinitely. Tasks are now bounded by `TASK_TIMEOUT` and report a `timeout` status.
- **`sleep_mode()` crashed on every call** with `NameError: BASE_DIR` (it used an undefined name instead of `paths.ROOT`).
- **11 advertised tools always raised `NameError`**: `get_contacts`, `get_contact_by_id`, `list_sensors`, `get_sensor_data`, `set_wallpaper`, `take_photo`, `record_video`, `record_audio`, `pick_file`, `share_file` and `share_text` were in the tool schema and the dispatch table but were never importable.
- **Phantom `tools_core` module**: Five call sites imported a module that never existed, and the bare `except ImportError` swallowed it — silently disabling progressive chunk summarisation, all WhatsApp auto-replies and the WhatsApp log.
- **HTTP 400 exhausted the whole key pool**: An invalid request was retried against every key and marked healthy keys as exhausted. It now skips the model immediately.
- **`generate_image()` always failed**: 4 of the 6 model IDs returned 404 (hiding the real error behind a bogus "model not found"), and the response parser only handled one of the two response shapes the API returns.
- **Piped stdin crashed the CLI** with `termios.error`; a corrupt `config.json` killed the chat loop every turn; `list_sensors` returned garbage; the WhatsApp log stored sender id and name in swapped fields.
- **Permissions duration regex**: Now accepts `MM:SS` / `HH:MM:SS` formats in addition to bare seconds.

- **`generate_image()` always failed**: 4 of the 6 model IDs returned 404 (hiding the real error behind a bogus "model not found"), and the response parser only handled one of the two response shapes the API returns.
- **Piped stdin crashed the CLI** with `termios.error`; a corrupt `config.json` killed the chat loop every turn; `list_sensors` returned garbage; the WhatsApp log stored sender id and name in swapped fields.
- Config persistence race conditions between different modules
